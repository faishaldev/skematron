# Rules: apps/web (dashboard)

Read before changing anything in `apps/web/`. These rules add to AGENTS.md and never relax it.

## What it is

- **The Skematron dashboard.** It runs in single-organization mode:
  - The installation has exactly one organization, created by first-run setup (`/setup`).
  - After setup, people join by invitation only.
- **Stack:**
  - Next.js 16 (App Router, Turbopack), React 19 and Better Auth 1.7 (email and password, plus the organization plugin).
  - Prisma 7 for the metadata database only (see `ai/rules/metadata.md`).
  - Before writing Next.js code, read the version-matched docs in `apps/web/node_modules/next/dist/docs/`.
  - `apps/web/AGENTS.md` is generated by `next dev`. Commit it, and do not edit it.
- **Not multi-tenant yet.** Hosted SaaS mode needs these first:
  - an SSRF guard for user-supplied database hosts (AGENTS.md "Security")
  - quotas and entitlements

## Authentication and authorization

- Every page, server action and route handler calls `requireActor()` or `requirePermission()` from `lib/session.ts`. Layouts render navigation only; they are not a security boundary.
- **Permissions come from `lib/roles.ts` only:** viewer < member < admin < owner.
  - Change it there, update its tests, and update the table in `ai/knowledges/architecture.md`.
  - The UI hides what a role cannot do, and the server still refuses it.
- **Every query is scoped to `actor.organizationId`:** look projects up by organization and slug, and everything else through its project.
- **Sign-up is invitation-only,** enforced by `maySignUp` in Better Auth's `user.create.before` hook. Never weaken that gate.
- **Organization changes:** member changes go through Better Auth's API with the request headers, after the app's own checks in `lib/members.ts`:
  - no escalation above your own role
  - the owner is protected
  - no self-changes
- **Better Auth's own config:**
  - The owner role cannot delete the organization.
  - Users cannot create organizations.
  - Telemetry stays disabled.

## Secrets and user databases

- Connection URLs are validated by `lib/connections.ts`: postgresql only, and an allow-list of parameters, with no file-reading SSL parameters.
- They are stored only encrypted (`lib/secrets.ts`, AES-256-GCM, `SKEMATRON_SECRET_KEY`).
- **Never send a URL, password or decrypted secret** to the browser, the HTML, logs, audit details or error messages. Show `connectionHint` only.
- **Only `lib/targets.ts` decrypts and connects.** It only introspects, read-only. Nothing in the app writes to a user database. Apply needs its own design and authorization flow.
- Edit forms never pre-fill a stored URL. An empty field means "keep the current one".

## Data rules

- **Schema versions are immutable.**
  - `lib/versions.ts` stores the snapshot in `@skematron/storage` first. Then, under a per-project advisory lock, it records the next number, or reports "unchanged".
  - Never update or delete a version.
- **Audit every privileged action** with `recordAudit` (`lib/audit.ts`). Add new actions to its `AuditAction` type.
- Configuration comes from `lib/env.ts`. It is read lazily and must fail with a clear message.

## Code conventions

- **Server actions use `runAction()`** from `lib/actions.ts`. They redirect with `?notice=` or `?error=`, and only `messageFor()` decides what an error may show.
- Validate every form field and URL parameter. Route parameters reach `lib/` functions only through validated lookups.
- Use server components by default. There are no client components yet; add one only when an interaction needs it.
- **Domain logic stays in `@skematron/core` and `@skematron/adapters`.** `lib/` modules hold the app logic and are testable with `node:test`:
  - Pure modules: `roles`, `secrets`, `connections`, `slugs`.
  - Metadata modules, covered by `lib/metadata.integration.test.ts`.
- Keep `lib/auth.ts` free of `server-only`, so the Better Auth CLI can load it.
- `pnpm typecheck` runs `next typegen`, then `tsc`. `next build` must keep passing.
