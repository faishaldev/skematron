# Rules: apps/web (dashboard)

Read before changing anything in `apps/web/`. These rules add to AGENTS.md and never relax it.

## What it is

- **The Skematron dashboard.** It runs in single-organization mode:
  - The installation has exactly one organization, created by first-run setup (`/setup`).
  - After setup, people join by invitation only.
- **Stack:**
  - Next.js 16 (App Router, Turbopack), React 19 and Better Auth 1.7 (email and password, plus the organization plugin).
  - Prisma 7 for the metadata database only (see `ai/rules/metadata.md`).
  - Before writing Next.js code, read the version-matched docs in `apps/web/node_modules/next/dist/docs/`.
  - `apps/web/AGENTS.md` is generated by `next dev`. Commit it, and do not edit it.
- **Not multi-tenant yet.** Hosted SaaS mode needs these first:
  - an SSRF guard for user-supplied database hosts (AGENTS.md "Security")
  - quotas and entitlements
  - stronger shadow-database isolation: members can run SQL there through Prisma's `dbgenerated(...)` (decision D17)

## Authentication and authorization

- Every page, server action and route handler calls `requireActor()` or `requirePermission()` from `lib/session.ts`. Layouts render navigation only; they are not a security boundary.
- **Permissions come from `lib/roles.ts` only:** viewer < member < admin < owner.
  - Change it there, update its tests, and update the table in `ai/knowledges/architecture.md`.
  - The UI hides what a role cannot do, and the server still refuses it.
- **Every query is scoped to `actor.organizationId`:** look projects up by organization and slug, and everything else through its project.
- **Sign-up is invitation-only,** enforced by `maySignUp` in Better Auth's `user.create.before` hook. Never weaken that gate.
- **Organization changes:** member changes go through Better Auth's API with the request headers, after the app's own checks in `lib/members.ts`:
  - no escalation above your own role
  - the owner is protected
  - no self-changes
- **Better Auth's own config:**
  - The owner role cannot delete the organization.
  - Users cannot create organizations.
  - Telemetry stays disabled.

## Secrets and user databases

- Connection URLs are validated by `lib/connections.ts`: postgresql only, and an allow-list of parameters, with no file-reading SSL parameters.
- They are stored only encrypted (`lib/secrets.ts`, AES-256-GCM, `SKEMATRON_SECRET_KEY`).
- **Never send a URL, password or decrypted secret** to the browser, the HTML, logs, audit details or error messages. Show `connectionHint` only.
- **Only `lib/targets.ts` decrypts environment URLs and connects to user databases.** It only introspects, read-only. Nothing in the app writes to a user database. Apply needs its own design and authorization flow.
- **SQL derived from user input runs only in the shadow database** (`lib/shadow.ts`): Prisma's DDL and migration plans.
  - It uses a fresh `skematron_shadow_*` database per run, drops it afterwards, and refuses a superuser role.
  - Never run such SQL anywhere else, and never point the shadow URL at a server with real data.
- **The Prisma CLI** runs only through `lib/prisma-import.ts`: in a temporary directory, with a timeout, and with an environment that contains none of Skematron's secrets. Connection URLs are removed from a schema before it is run or stored.
- Edit forms never pre-fill a stored URL. An empty field means "keep the current one".

## Data rules

- **Schema versions are immutable.**
  - `lib/versions.ts` stores the snapshot in `@skematron/storage` first. Then, under a per-project advisory lock, it records the next number, or reports "unchanged".
  - Never update or delete a version.
- **Main changes only by merging a branch** (`lib/branches.ts`). The only exception is the baseline: the first `schema.prisma` import or environment import. Never add another path that records versions directly.
- **Branches:**
  - Change a head only through `updateHead`, which checks `updatedAt` (no lost updates), records the contributor, and sends the review back to draft.
  - The editor works only for "dashboard" projects and uploads only for "code" projects (`requireSchemaSource`), so a project never has two sources of truth.
  - Every editor edit goes through core's edit functions, then `normalizeSnapshot` in the shadow database. Never store a typed fragment without that round trip. Check typed names, types and defaults with `lib/schema-input.ts` first.
  - Merge only through `mergeBranch`. It requires an approval of the current test run for exactly the current head, and records the version with `basedOn` and `onCreated` in one transaction.
  - A closed or merged branch never changes again.
- **Migrations** (`lib/migrations.ts`) review branches:
  - Revisions and reviews are immutable; only `Migration.status` (and `toVersionId` at merge) change, under the per-migration advisory lock.
  - A test run counts only if it was made after the branch's last change (`testedRevision`).
  - Submitting needs changes, zero open questions, zero unsupported changes and a passed, current test run.
  - Approve or reject needs `review-migrations`, and the reviewer must not have worked on the branch (`authorsOf`). Approving destructive operations needs an explicit acknowledgment, rejecting needs a comment, and the reviewed revision id must still be the latest.
- **Audit every privileged action** with `recordAudit` (`lib/audit.ts`). Add new actions to its `AuditAction` type.
- Configuration comes from `lib/env.ts`. It is read lazily and must fail with a clear message.

## Pages and wording

- **Navigation lives in the sidebar** (`app/(app)/layout.tsx`, `components/sidebar-nav.tsx`):
  - At the top is a project switcher: a native `<details>` menu with the projects, "View all projects" and "New project". That is the only way to the list of projects.
  - The list of projects (`/projects`) is a grid of cards. Creating a project is its own page, `/projects/new`, which every "New project" link opens.
  - Below it are the current project's sections, with icons from `components/icons.tsx`: Overview, Branches (with the number of open branches), Main versions, Diagram, Databases and Settings.
  - **The sections are always there.** Outside a project (the projects list, members, audit log), the sidebar shows the last project you opened, or else the first one.
    - The client sidebar remembers the last project in the `skematron_last_project` cookie, which holds only a slug.
    - The layout uses it only if it is one of the member's projects.
  - Then the Workspace group (Members, Audit log, for admins), then the account.
  - Give a new project-level area its own page under `projects/[project]/` and a sidebar entry, rather than another section on the overview.
  - Pages load the project with `resolveProject` (`lib/project-pages.ts`).
- **Show the schema as a diagram first** (`components/diagram.tsx`, `SchemaDiagram`):
  - It is server-rendered SVG with no layout library: referenced tables on the left, links as curves, and links between distant columns on lanes above the tables.
  - Color a branch's changes with `diagramHighlights(plan)`, which takes the planner's plan. Never compare raw JSON: JSONB reorders keys.
  - The detailed tables (`SchemaView`) are the second view.
- **Every page starts the same way:** `Breadcrumbs`, then `PageHeader` (title, optional badge and subtitle, main actions on the right), then `Flash`. These and `Callout`, `Steps`, `Empty` and `Stat` are in `app/components/ui.tsx`.
- **Tell people what to do next.** Pages with a workflow (project, branch) show one `Callout` with the next step and its button. Empty lists use `Empty` and say how to fill them.
- **Plain language first, SQL second.** Plans are shown with `PlanView`: one sentence per change (`describeOperation`), its risk and warnings, and the SQL behind a `<details>`. Technical steps (sequences, temporary defaults) are folded away. Checksums, history and downloads go into `<details>` too.
- **Words people use:** "test run", not "shadow check"; "database", not "environment", in headings; "Deletes data", not "destructive", in badges. Keep stored values and audit actions unchanged.
- Style with the classes in `app/globals.css` (`button`/`.button`, `.primary`, `.card`, `.card.flush`, `.callout`, `label.option`, `.accordion`, `.narrow-page` for a page that is a single form). Both light and dark mode must work.

## Code conventions

- **Server actions use `runAction()`** from `lib/actions.ts`. They redirect with `?notice=` or `?error=`, and only `messageFor()` decides what an error may show.
- Validate every form field and URL parameter. Route parameters reach `lib/` functions only through validated lookups.
- Use server components by default. The only client component is the sidebar's link list, which needs the current path to highlight where you are. Add another only when an interaction needs it. Collapsible parts use `<details>` and view switches use links (`?view=`), which need no JavaScript.
- **Domain logic stays in `@skematron/core` and `@skematron/adapters`.** `lib/` modules hold the app logic and are testable with `node:test`:
  - Pure modules: `roles`, `secrets`, `connections`, `slugs`.
  - Metadata modules, covered by `lib/metadata.integration.test.ts`.
- Keep `lib/auth.ts` free of `server-only`, so the Better Auth CLI can load it.
- `pnpm typecheck` runs `next typegen`, then `tsc`. `next build` must keep passing.
